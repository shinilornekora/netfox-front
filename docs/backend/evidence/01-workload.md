# Паспорт нагрузки Плёнки (РХД ПР-1)

Требование ПР-1 к домашней системе:

- одна критическая изменяющая операция и одна операция чтения;
- не меньше трёх инвариантов с указанием, чем защищён каждый;
- объём и распределение данных;
- фиксированная конкурентность и согласованный с ней пул;
- три повторяемых запуска;
- вывод.

Замер идёт **сквозь весь путь запроса**, как у браузера: gateway (CSRF, сессия из кэша, лимиты, подпись личности) → сервис → PostgreSQL (RLS, транзакция, outbox). Это сознательно не голый SQL, как в учебном примере: у Плёнки узким местом может оказаться не база, и замер должен это показать.

Генератор — `tools/loadgen`. Сырые выводы **всех** запусков лежат в `docs/evidence/raw/`. В таблицах ниже — все три повтора, а итог считается по **медиане повторов**, а не по лучшему.

## Окружение

- Стенд: 2 vCPU Intel Xeon 2.1 GHz, 7 ГБ RAM, Linux. Генератор, gateway, четыре сервиса, PostgreSQL и Kafka работают на одной машине.
- Go 1.26.0, PostgreSQL 16.15 (`shared_buffers` 128 МБ, остальное по умолчанию), Kafka 3.9.1 в Docker.
- Сервисы запущены бинарниками, данные — в схемах одной базы, как в `deploy/compose.yaml`. Во время замера работают ретранслятор outbox billing и потребитель событий заказов в playback: каждая покупка порождает два события (charging и completed) и два upsert одной строки проекции.
- Дата опыта: 15.11.2026, версия кода — с outbox в billing (TRADEOFFS 4.17).

## Операции

### Сценарий watch — то, что делает смотрящий зритель

- **Запись** (критическая по объёму): `PUT /api/playback/progress` — пинг плеера раз в 10 секунд. Это один `INSERT … ON CONFLICT DO UPDATE … WHERE client_ms <` в транзакции с RLS-контекстом. 10 000 одновременно смотрящих дают 1 000 таких записей в секунду.
- **Чтение:** `GET /api/playback/continue` — лента «Продолжить просмотр» (прогресс зрителя + реплика каталога, RLS).
- **Соотношение** 80/20 задаётся номером задания (`i % 5 == 4` — чтение), поэтому оно одинаковое в каждом повторе.
- **Пользователи:** 200 зрителей с подпиской, задания идут по ним по кругу.
- **Подготовка** (в замер не входит): регистрация напрямую в identity, мимо лимита 10 регистраций в минуту с IP; оформление подписки; старт просмотра.
- **Прогрев:** по одному чтению на зрителя. Прогреваются кэш сессий gateway, кэш решений о доступе и соединения пулов.

### Сценарий checkout — критическая по деньгам запись

- `POST /api/billing/checkout` — покупка фильма. Внутри: SERIALIZABLE-шаг prepare (заказ + событие в outbox), вызов банка (симулятор), SERIALIZABLE-шаг fulfil (покупка + статус + событие).
- **Пользователи:** каждое задание — новый зритель, `requests × runs` зарегистрированы заранее. Все покупают один фильм. «Горячий» объект — один тайтл, но строки у всех разные, поэтому правильный результат — ноль конфликтов.

### Общие параметры

- `requests per run`: 2 000 для watch, 1 000 для checkout; `runs`: 3; `workers`: 1, 8, 32.
- **Пулы соединений сервисов:** playback 20, billing 15, identity и catalog 10. При `workers=32` часть запросов ждёт соединение. Так и задумано (обратное давление), и это зафиксировано здесь.
- **Лимит на пользователя** — 300 запросов в минуту. Он не достигается: ~10 запросов на зрителя за опыт.
- **Как считается время:** полное, до последнего байта ответа. Процентили — методом ближайшего ранга. Предел опыта — 60 с для watch и 120 с для checkout; ни один опыт в него не упёрся.

## Целевые показатели опыта (SLO)

- error rate = 0 для обоих сценариев;
- watch: p95 < 50 мс для записи и чтения при `workers ≤ 32`;
- checkout: p95 < 100 мс при `workers ≤ 8`.

## Что нашёл замер: ложные конфликты SERIALIZABLE

Первая версия замера (100 покупок на повтор, ещё без outbox в billing) показала: при 8 параллельных покупках около 1% покупок заканчивались ошибкой 500. Медиана была 5–7 мс, а p95 — около 110. В логе PostgreSQL на `INSERT INTO orders` стояло `could not serialize access due to read/write dependencies… Canceled on identification as a pivot, during write`.

Причина — **ложные конфликты SSI**. Покупатели разные и строки разные, но:

1. Проверка «нет ли у зрителя заказа в работе» в **обобщённом** плане шла по частичному индексу `orders_stuck_idx`. pgx выполняет запросы подготовленными, поэтому план обобщённый. Индекс построен по `updated_at` с условием `status IN ('charging','refunding')`, а `user_id` фильтровался уже после чтения. Получалось чтение всего индекса, то есть предикатная блокировка на весь индекс. При этом каждая новая покупка вставляет туда свой заказ в статусе `charging`. Любая пара одновременных покупок образовывала опасную структуру, и после шести попыток транзакция сдавалась.
2. На почти пустой таблице (свежая установка) планировщик выбирает последовательное сканирование, а оно блокирует уже всю таблицу.

Исправление (`services/billing/migrations/002_inflight_idx.sql`, `kit/pgkit/pgkit.go`):

- **индекс** `orders (user_id, status)`, а `orders_stuck_idx` стал полным `(status, updated_at)`;
- внутри SERIALIZABLE-транзакций **`SET LOCAL enable_seqscan = off`** — это совет документации PostgreSQL для SSI;
- исчерпанные попытки возвращают **503 `contention`** вместо 500, и клиент повторяет запрос с тем же `Idempotency-Key`.

До и после — на одних данных (100 000 заказов) и одном стенде, по 100 покупок на повтор, 8 потоков. Сырые выводы — `raw/fix_before_100k_w8.txt` и `raw/fix_after_100k_w8.txt`, ещё один «до» на маленькой базе — `raw/fix_before_small_db_w8.txt`.

| | ошибок | p95 по повторам, мс | медиана p95, мс | throughput по повторам, /с | медиана, /с |
|---|---:|---|---:|---|---:|
| до (100 тыс. заказов) | 3 из 300 | 107.9 / 118.6 / 70.7 | 107.9 | 233 / 235 / 219 | 233 |
| до (маленькая база, ~650 заказов) | 4 из 300 | 111.9 / 113.1 / 65.1 | 111.9 | 242 / 217 / 256 | 242 |
| после (100 тыс. заказов) | 0 из 300 | 33.1 / 18.1 / 16.7 | 18.1 | 550 / 701 / 693 | 693 |

Медиана p95 снизилась со 108 до 18 мс, пропускная способность выросла втрое (по отдельным повторам ×2,4–3,2). Регрессионный тест — `TestInFlightCheckUsesUserIndex`: он проверяет обобщённый план и 64 покупки разных зрителей при 8 параллельных.

Почему нынешние цифры покупки (p95 ~40 мс при 8 потоках) выше, чем «после» (~18). Это другой опыт:

- повторы в 10 раз длиннее (1 000 покупок), так что короткий прогретый всплеск больше не скрывает очередь;
- каждая покупка теперь дополнительно пишет два события в outbox;
- ретранслятор и потребитель событий в playback делят с замером те же два ядра.

Сравнивать эти числа напрямую нельзя, и РХД-01 это прямо запрещает: изменились код и длина опыта.

Остаток, который честно признаём: на почти пустой таблице единичные транзакции всё ещё исчерпывают попытки уже при 8 параллельных покупках. Таблица умещается в одну-две страницы индекса, а SSI блокирует страницами. Регрессионный тест (64 покупки, 8 потоков) под `-race` в 6 из 12 прогонов получил 1–3 ответа 503; как и настоящий клиент, он повторяет запрос с тем же `Idempotency-Key`, и все 64 покупки оплачены. В замере на 100 тыс. заказов таких ответов ноль.

## План чтения ленты «Продолжить»

Полный вывод — `raw/explain_continue.txt`. `EXPLAIN (ANALYZE, BUFFERS)` снят под ролью `playback` с RLS-контекстом:

- `Index Scan using progress_continue_idx` по `user_id`;
- затем hash join с репликой каталога (Seq Scan по 21 строке: 16 опубликованных прошли фильтр, 5 снятых отброшены; на такой таблице это дешевле индекса);
- затем сортировка одной-двух строк.

**Execution Time 0.107 мс, 7 буферов, все попадания в кэш.** Сквозной p50 при `workers=1` — 1.0 мс, то есть в базе проходит около 10% времени запроса. Остальное — HTTP, gateway и сериализация.

## Вывод

**Какой ресурс ближе всего к исчерпанию.** Процессор стенда, и это замерено, а не выведено. Пропускная способность watch растёт с 1 до 8 потоков (~710 → ~2 000 запросов опыта в секунду, из них пингов прогресса ~1 600), а с 8 до 32 — едва (~2 000 → ~2 400/с), при этом p95 растёт втрое: запросы стоят в очереди.

Отдельный длинный прогон при 32 потоках (30 000 запросов, 13 с) снят с `vmstat` и `top` — `raw/cpu_watch_w32.txt`:

| | доля процессора (100% = одно ядро, всего 200%) |
|---|---:|
| простой всей машины | ~10% |
| PostgreSQL, все процессы | ~56% |
| playback | ~48% |
| gateway | ~44% |
| генератор нагрузки | ~27% |

Машина занята на ~90%. Крупнейший отдельный потребитель — PostgreSQL (~56% из 200%, все процессы вместе), но два Go-сервиса на пути запроса (gateway и playback: HTTP, JSON, проверка подписи) вместе тратят больше — ~92%. В самой базе запрос ленты занимает 0.1 мс: база загружена числом коротких транзакций, а не их тяжестью.

**Что делает замер оптимистичным:**

- прогретый кэш (все данные в `shared_buffers`);
- равномерное распределение нагрузки по зрителям;
- замкнутый цикл генератора: новый запрос уходит только после ответа, а при реальном открытом потоке очереди были бы длиннее;
- отсутствие сетевых задержек между процессами на одной машине.
- генератор нагрузки сам работает на том же стенде и занимает ~27% процессора (`raw/cpu_watch_w32.txt`): часть узкого места создаёт сам замер, на отдельной машине генератора пропускная способность сервисов была бы выше.

**Что оправдало бы реплику, производное представление или разделение по узлам.** Не нынешние цифры:

- **реплика для чтения** имела бы смысл, если бы *в базе* чтение ленты (сейчас 0.1 мс) стало заметной частью p95 при росте `progress`;
- **разделение playback по узлам** (по `user_id`) — если запись прогресса упрётся в WAL или ввод-вывод одного узла. Чтобы это проверить, нужен отдельный замер: открытый поток 1 000+ пингов в секунду на выделенной под базу машине и метрика времени коммита.

Первым шагом при росте был бы не шардинг, а вынос сервисов и базы на разные машины: сейчас они делят процессор.

**Главное.** Замер нашёл реальный дефект — ложные конфликты SERIALIZABLE. Функциональные тесты его не находили: покупки там шли по одной. Это и есть цена выбора SERIALIZABLE (TRADEOFFS 3.1, 3.11): корректность бесплатна для кода, но планы запросов приходится держать под контролем.

## Как повторить

```
# стенд поднят, seed выполнен; id тайтлов — из GET /api/titles
cd tools
go run ./loadgen -base http://localhost:8080 -identity http://localhost:8081 \
  -mix watch -film <id фильма по подписке> -users 200 -workers 8 -requests 2000 -runs 3
go run ./loadgen -base http://localhost:8080 -identity http://localhost:8081 \
  -mix checkout -paid <id платного фильма> -workers 8 -requests 1000 -runs 3 -timeout 120s
```

В `deploy/compose.yaml` identity наружу не опубликован. Без `-identity` регистрация пойдёт через gateway и упрётся в лимит 10 регистраций в минуту с одного IP (`AuthLimit` в `services/gateway/cmd/main.go`). Для опыта checkout нужно пробросить порт 8080 сервиса identity (`ports: ["8081:8080"]`). В этом замере сервисы работали бинарниками, и identity слушал порт 8081 напрямую.
