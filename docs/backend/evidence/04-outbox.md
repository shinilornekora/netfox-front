# Transactional outbox и надёжный потребитель (РХД ПР-4, ПР-5)

Требования к домашней системе:

- **ПР-4.** Изменение бизнес-объекта, запись события и ответ команды фиксируются одной транзакцией. Нужны тесты на успешную фиксацию, повтор запроса, конфликт изменённого содержимого под прежним ключом и откат при ошибке после записи события. Изоляция outbox подтверждается RLS. Для контракта описано назначение каждого поля и алгоритм потребителя при повторной доставке.
- **ПР-5.** Надёжный обработчик формирует локальную проекцию. Отметка inbox и полезное действие — одна транзакция. Изоляция обеспечена RLS под непривилегированной ролью (в Плёнке — `playback_app`: не владеет таблицами, не может снять RLS, тест `TestNegativeDataRoleCannotDisableRLS`). Внешние операции ограничены жёсткими тайм-аутами. Есть воспроизводимые сценарии: повторная доставка, падение после коммита, poison pill в DLQ.

## Доменная операция: оформление заказа в billing

`POST /api/billing/checkout` с заголовком `Idempotency-Key`. Сага оплаты (TRADEOFFS 4.8) проходит три локальные транзакции, и **в каждой** вместе меняются заказ и outbox:

| Шаг | Транзакция | Что пишется вместе |
|---|---|---|
| prepare | SERIALIZABLE | строка `orders` (бизнес-объект, `status=charging`) + `idem_key` и `request_hash` (сохранённый ответ команды: повтор с тем же ключом возвращает этот заказ) + событие `charging` |
| fulfil | SERIALIZABLE | `purchases` или `subscriptions` + `orders.status=completed` + событие `completed` |
| переход | READ COMMITTED | `orders.status` (`failed`, `refunding`, `refunded`) + событие с новым статусом |
| возврат выданного | SERIALIZABLE | удаление `purchases` или закрытие `subscriptions` + `orders.status=refunding` + событие `refunding`; после банка — переход `refunded` |

Возврат выданного — `POST /api/billing/admin/orders/{id}/refund` (только администратор; в админке — кнопка «Вернуть» в «Продажах»).

Код: `services/billing/internal/adapter/pgsql/pgsql.go` → `InsertOrder`, `Fulfil`, `Revoke`, `Transition`, `orderEvent`. Таблица и политики — миграция `services/billing/migrations/003_outbox.sql`. Ретранслятор — `kit/outbox` (аренда и публикация вне транзакции, TRADEOFFS 4.3).

### Почему RLS на outbox устроена именно так

У outbox нет «арендатора»: это служебная очередь сервиса. Изолируется не зритель от зрителя, а **код оплаты от очереди**. Защита в два слоя (TRADEOFFS 3.8, 4.17):

1. **Права.** Запросы пользователей идут под ролью данных `billing_app`. На `outbox` у неё есть только `INSERT` (`migrations.Deny`). Читать, отмечать и удалять события может только владелец схемы `billing`, под которым работает ретранслятор. Ни ошибка, ни SQL-инъекция в коде оплаты не прочитает и не сотрёт события: у роли нет на это прав, а снять RLS может только владелец.
2. **RLS с `FORCE`.** Даже код под ролью-владельцем видит очередь, только если транзакция объявила себя ретранслятором: `set_config('plenka.relay','on', true)`. Это защита от ошибки в коде владельца (миграции, обслуживание), а не от атаки: объявить себя ретранслятором может любой код с правами владельца.

## Контракт `billing.orders.v1`

Конверт (`contracts/events/events.go` → `Envelope`) общий для всех событий системы:

| Поле | Назначение |
|---|---|
| `id` | UUID события. **Ключ дедупликации** у потребителя (inbox). Повторная доставка приходит с тем же `id`. |
| `type` | `order.status_changed`. По нему потребитель выбирает обработчик. |
| `schema_version` | версия структуры `data` внутри топика. Совместимые изменения — только добавление полей. Несовместимые — новый топик `.v2` (TRADEOFFS 4.16). |
| `aggregate_id` | id заказа. Это же ключ сообщения Kafka, поэтому события одного заказа идут в одну партицию по порядку. |
| `revision` | номер шага саги: `charging` 1 → `completed`/`failed` 2 → `refunding` 3 → `refunded` 4 (`events.OrderRevision`). Допустимые переходы его только увеличивают, и потребитель отбрасывает события с ревизией не больше сохранённой. |
| `occurred_at` | время создания события в outbox (UTC). Только для диагностики, порядок по нему не определяется. |
| `source` | `billing` — кто издал. |
| `correlation_id` | `Idempotency-Key` исходной команды: связывает событие с запросом клиента в логах. |
| `data` | JSON `OrderSnapshot` (в конверте — base64, так сериализуется `[]byte` в Go). |

`OrderSnapshot`:

| Поле | Назначение |
|---|---|
| `order_id` | id заказа (= `aggregate_id`) |
| `user_id` | зритель. Потребитель выставляет по нему контекст RLS |
| `kind` | `purchase` или `subscription` |
| `title_id` | для покупки — какой фильм |
| `plan_id` | для подписки — тариф |
| `amount_kopecks` | сумма в копейках (TRADEOFFS 2.12) |
| `status` | статус **после** перехода |
| `changed_at` | время перехода в billing |

Событие — **снимок**, а не дельта: любое одно событие восстанавливает состояние заказа в проекции целиком (TRADEOFFS 2.5).

### Алгоритм потребителя при повторной доставке

Реализация — `playback`: `usecase.HandleOrders` → `pgsql.ApplyOrder`.

1. Разобрать конверт и проверить идентификаторы. Если он битый (не JSON, нет `id`), не разбирается `data` или `order_id`/`user_id`/`title_id` — не UUID, это постоянная ошибка (`bus.Permanent`); ошибки данных PostgreSQL классов 22 и 23 и отказ политики RLS (событие пишет заказ не тому зрителю) — тоже (`bus.IsPermanent`). Сообщение уходит в `<topic>.dlq` с причиной в заголовке, и только после успешной публикации в DLQ фиксируется смещение. Недоступна DLQ — публикация повторяется, смещение не фиксируется. **Временная** ошибка (база недоступна, тайм-аут) в DLQ не уходит: потребитель повторяет с паузой до 5 с, пока не получится; после 4 неудач — тревога в логе. Партиция стоит, но корректное событие не теряется и порядок не нарушается (TRADEOFFS 4.18, Д15).
2. Открыть транзакцию и выставить контекст RLS `plenka.user_id = data.user_id`.
3. `INSERT INTO inbox(event_id) … ON CONFLICT DO NOTHING`. Если вставилось 0 строк, событие уже обработано: зафиксировать и выйти. **Это и есть обработка повтора.**
4. Upsert проекции `order_feed` по `order_id` с условием `WHERE order_feed.revision < EXCLUDED.revision`. Опоздавшее старое событие ничего не меняет.
5. Зафиксировать транзакцию. Inbox и проекция фиксируются вместе или не фиксируются вовсе.
6. Только после фиксации, если статус `refunding` или `refunded`, сбросить кэш решений о доступе для пары «зритель — фильм» (для подписки — все решения зрителя). Если процесс упадёт между шагами 5 и 6, событие придёт снова, но шаг 3 его отсечёт. Тогда кэш доживёт свои 5 минут — это то же окно, что и без события.
7. Смещение Kafka фиксируется вручную (`kgo.DisableAutoCommit`, `CommitRecords`) и только для записей, судьба которых решена: обработана или лежит в DLQ. Упали после шага 5, но до фиксации смещения — получим повтор, см. шаг 3.

Каждая попытка обработки ограничена тайм-аутом контекста (`bus.Consumer.Timeout`, по умолчанию 10 с). Публикация в DLQ и транзакции ретранслятора тоже идут с тайм-аутами. Зависшая база не держит партицию бесконечно.
